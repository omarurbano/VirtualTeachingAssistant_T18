## Sprint 4 Deliverables

**Period:** August 27 – September 30, 2026  
**Suggested Outcome:** Complete at least 80% of the planned project features and demonstrate meaningful, integrated progress.

**Sprint Goal:** Automate the synthetic data generation pipeline from the existing OneDrive course files, execute QLoRA fine-tuning on NVIDIA Brev A100 infrastructure, and produce a validated, LoRA-ready dataset with a trained adapter ready for integration.

| Deliverable | Details and Acceptance Criteria | Owner(s) | Report Evidence |
|-------------|--------------------------------|----------|-----------------|
| 1. OneDrive-Synced Automated Synthetic Data Pipeline | Configure and validate the end-to-end pipeline in `Synthetic_Data_Generation/gen_data.py` operating in `--mode onedrive` against the locally synced OneDrive course folder. Pipeline flow: file discovery → text extraction via Unstructured → paragraph-aware chunking (≤1200 chars, ≥120 chars minimum) → seed Q&A generation via NVIDIA NIM (`meta/llama-3.1-70b-instruct`, 4 Q&A pairs per chunk) → instruction augmentation (≥3 variants per seed with randomized phrasing templates) → SHA-256 deduplication → LoRA-ready JSONL output with schema `{"instruction","input","output","tags","source_file","cognitive_level"}`. Acceptance criteria: single command `python gen_data.py --mode onedrive --input-dir <path> --variants 3` completes without manual intervention; final `training_dataset.jsonl` contains ≥1,500 validated records from ≥12 source files; each record passes validation (`instruction` ≥ 8 chars, `output` ≥ 20 chars); duplicate rate < 5%; output includes coverage of all major course topics (DBMS, SQL, ER Model, Normalization, Transactions, NoSQL, CAP Theorem, Concurrency Control). | Backend / ML team | Pipeline execution logs (timestamped), `output/training_dataset.jsonl` with line count, `output/quality_report.json` with per-source-file statistics, validation script output confirming acceptance criteria. |
| 2. NVIDIA Brev A100 Remote Execution & LoRA Fine-tuning | Automate the deploy-run-pull cycle using existing `scripts/brev_deploy.sh`, `scripts/brev_run.sh`, and `scripts/brev_pull.sh` so that a single local command triggers the full workflow on the NVIDIA Brev A100 instance. The remote pipeline (`remote_pipeline.sh`) must: create venv, install dependencies, run data generation, verify dataset existence, then execute `nemo_finetune/train_lora.py` with QLoRA config (4-bit NF4 quantization, `nvidia/nemotron-4-7b-instruct`, rank 16, alpha 32, 3 epochs, batch size 4, cosine scheduler, paged AdamW 8-bit). Acceptance criteria: `bash scripts/brev_run.sh onedrive --input-dir data/ --variants 3` executes end-to-end on Brev A100; training completes without OOM on A100 80GB; final training loss < 1.5; LoRA adapter saved to `lora_adapter/` with adapter weights + tokenizer; total pipeline runtime < 4 hours for current dataset; training logs show monotonically decreasing loss across epochs. | Backend / DevOps team | Brev execution logs, `nvidia-smi` output confirming A100 GPU utilization, training loss curve (CSV or TensorBoard-compatible), `lora_adapter/` directory checksums, total runtime metric, runbook documenting single-command execution. |
| 3. Synthetic Data Quality Assurance & Validation Framework | Implement a validation layer (`validate_dataset.py` or integrated into `gen_data.py`) that produces a structured quality report after every pipeline run. Checks: total record count, record count per source file, instruction-response length distribution (mean, median, p5, p95), duplicate rate (SHA-256 collision check), cognitive level distribution across Bloom's taxonomy levels, NIM API call success rate, augmentation success rate, and per-source coverage completeness. Output: `output/quality_report.json` plus human-readable `output/quality_report.md`. Acceptance criteria: validation report auto-generated after every pipeline run; duplicate rate < 5%; average instruction length ≥ 15 chars; average response length ≥ 40 chars; ≥ 80% of records tagged with at least one keyword tag; ≥ 70% of records assigned a cognitive level; report flags any source file with < 50 generated records for manual review. | Backend team | `output/quality_report.json` and `.md` from a successful pipeline run, validation script source code, before/after dataset statistics showing quality improvements, CI integration ensuring report generation on every run. |
| 4. Fine-tuned Model Evaluation & Benchmark Report | Evaluate the QLoRA-trained adapter against a held-out test set of 20–30 human-curated Q&A pairs derived directly from the course source material. Metrics: perplexity on test set, exact-match and fuzzy-match accuracy (BLEU-4 or ROUGE-L), and qualitative assessment of answer grounding and hallucination rate. Compare against the baseline `nvidia/nemotron-4-7b-instruct` without LoRA. Produce a structured evaluation report. Acceptance criteria: test set of ≥ 20 questions created and frozen before training; evaluation script reproducible from `eval_model.py`; fine-tuned model achieves ≤ 3.0 perplexity on test set; fine-tuned model shows ≥ 15% relative improvement in ROUGE-L over baseline; evaluation report documents per-question results, failure cases, and model limitations; no evidence of training data leakage in test set. | ML / Backend team | `eval_model.py` source, test set JSON file, evaluation report (HTML or PDF) with per-metric tables and sample inference comparisons, baseline vs. fine-tuned benchmark chart. |

**Major dependencies or risks:**

- **NVIDIA NIM API rate limits and availability:** Seed generation and augmentation depend on NIM API uptime. Mitigation: implement exponential backoff retries (already in `nim_client.py`), batch requests where possible, and cache NIM responses locally during development.
- **Brev instance availability and GPU allocation:** Brev A100 instances may have queue times or resource constraints. Mitigation: reserve instance in advance; maintain fallback to local CPU dry-runs for validation.
- **OneDrive sync conflicts and file availability:** Course files in the OneDrive-synced folder may be locked during sync or modified mid-pipeline. Mitigation: pipeline reads from snapshot copy; implement file locking checks; exclude temporary OneDrive files (`~*`, `*.tmp`).
- **Dataset quality and grounding:** Synthetic data may contain hallucinations if NIM-generated answers drift from source material. Mitigation: strict grounding prompts in `seed_generator.py`, validation layer checking answer-to-source overlap, human spot-check of 10% of generated records.
- **QLoRA training stability:** 4-bit quantization may cause training instability or OOM on smaller GPUs. Mitigation: use A100 80GB with paged AdamW 8-bit, gradient checkpointing, and gradient accumulation (already configured in `train_lora.py`).

**How will the client review the Sprint 4 work?**

The client will review: (1) the live end-to-end pipeline execution on the NVIDIA Brev instance, (2) the generated `training_dataset.jsonl` with quality report confirming acceptance criteria, (3) the LoRA adapter artifact and training metrics, and (4) the evaluation benchmark report comparing the fine-tuned model against the base model. The team will provide a 20-minute Sprint 4 demo video (unlisted YouTube) showing the single-command pipeline trigger, dataset statistics dashboard, training progress, and sample model inference outputs with citations. The client will validate dataset coverage against the known CPT_S course syllabus.

## Sprint 5 Deliverables

**Period:** October 1 – October 31, 2026  
**Suggested Outcome:** Reach 100% feature completion and focus on integration, deployment, testing, and defect resolution.

**Sprint Goal:** Integrate the fine-tuned LoRA adapter into the live Virtual Teaching Assistant backend, complete production deployment, implement real-time WebSocket updates, and achieve ≥ 80% test coverage with CI/CD automation.

| Deliverable | Details and Acceptance Criteria | Owner(s) | Report Evidence |
|-------------|--------------------------------|----------|-----------------|
| 1. Fine-tuned Model Integration into RAG Pipeline | Replace or extend the current answer generator in the Flask/Express backend to load and serve the QLoRA adapter. Create a new API endpoint (e.g., `POST /api/v1/query-finetuned`) that accepts a student question, retrieves relevant course chunks from the existing vector store, constructs a grounded prompt, and generates an answer using the fine-tuned LoRA model served via HuggingFace `text-generation-inference` or vLLM on the Brev instance. Acceptance criteria: fine-tuned model endpoint returns answers within 5 seconds per query; model correctly loads LoRA adapter on server restart without crashes; benchmark on 50 held-out course questions shows ≥ 70% answer relevance compared to current Gemini-based generation; API responses include citation metadata linking back to source files and page numbers. | Backend / ML team | API integration test suite (passing), benchmark comparison report (fine-tuned vs. current), latency metrics (p50, p95, p99), model serving logs showing successful adapter loading, updated API documentation. |
| 2. Production Deployment with Nginx + SSL + Process Management | Deploy the full stack (Flask/Express backend, student frontend, instructor dashboard, model serving endpoint) on a production server. Configure Nginx as reverse proxy with SSL via Let's Encrypt, set up systemd service files for auto-restart of backend processes, configure environment variable management, and enable access logging and error monitoring. Acceptance criteria: application accessible via HTTPS at production domain with valid SSL certificate; Nginx correctly proxies API and static file routes; all backend processes auto-restart on failure; health check endpoint (`/health`) returns HTTP 200; system remains stable under 24-hour continuous operation; SSL certificate auto-renewal configured. | DevOps team | Nginx configuration files, systemd unit files, SSL certificate details, deployment runbook with step-by-step instructions, uptime monitoring screenshot showing 24-hour stability, health check test results. |
| 3. WebSocket Real-time Query Streaming | Implement WebSocket infrastructure using Socket.io or native `ws` library to push live status updates to both student and instructor frontends during the query lifecycle. Status stages: `received` → `retrieving` → `generating` → `complete` (with error states). Instructor dashboard receives aggregated real-time feed of all active student queries. Acceptance criteria: student UI shows animated status indicator during query processing; instructor dashboard displays live query feed with student names and query topics; WebSocket automatically reconnects with exponential backoff on network interruption; works across Chrome, Firefox, and Safari; server handles ≥ 50 concurrent WebSocket connections without message loss. | Frontend / Backend team | WebSocket connection and message logs, frontend demo video showing real-time status updates, reconnection test results (simulated disconnect/reconnect), cross-browser compatibility report, load test results for concurrent connections. |
| 4. Comprehensive Test Suite & GitHub Actions CI/CD | Build automated test coverage across the full stack. Backend: pytest unit tests for all Python modules (`text_extractor`, `seed_generator`, `nim_client`, `unified_document_processor`, Express routes) targeting ≥ 80% line coverage. Frontend: Playwright E2E tests covering student enrollment, course viewing, query submission, and instructor analytics viewing. CI/CD: GitHub Actions workflow running lint, unit tests, and E2E tests on every PR to `main`. Acceptance criteria: `pytest --cov` reports ≥ 80% backend coverage; Playwright suite passes for 4 critical user journeys (student enroll, student query, instructor view analytics, instructor manage course); CI pipeline passes on main branch with green badge; test execution time < 10 minutes; test results published as GitHub Actions artifacts. | Full team | pytest coverage HTML report, Playwright test report with screenshots on failure, CI workflow YAML file, GitHub Actions badge in README, test execution time metrics, test documentation. |

**Major dependencies or risks:**

- **Brev instance long-term availability:** Model serving endpoint depends on Brev A100 remaining accessible. Mitigation: export LoRA adapter in standard HuggingFace format; prepare fallback deployment on local GPU server or cloud VM.
- **Frontend-backend API contract drift:** Real-time WebSocket events must match frontend expectations. Mitigation: define TypeScript/JavaScript event schema in shared docs; integration tests validate event contracts.
- **Production server procurement:** May require WSU IT approval and provisioning time. Mitigation: begin provisioning request in Week 1; use staging environment during development.
- **Test flakiness in E2E suite:** Playwright tests may fail due to timing or external API dependencies. Mitigation: mock NIM API and Gemini API in test environment; use `expect` with generous timeouts and retry logic.

**How will the client review the Sprint 5 work?**

The client will review: (1) a live production deployment accessible via HTTPS, (2) the fine-tuned model serving answers through the integrated RAG pipeline with citations, (3) real-time WebSocket updates visible in both student and instructor UIs, and (4) the CI/CD pipeline with passing test suites and coverage reports. The team will provide a Sprint 5 demo video showing the full integrated system and a test coverage dashboard. Client feedback will be collected via a structured acceptance form covering functionality, performance, and UI/UX criteria.
